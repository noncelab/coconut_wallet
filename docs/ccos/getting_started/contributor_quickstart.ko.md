# CCOS 기여 시작하기

영문 버전: [contributor_quickstart.en.md](./contributor_quickstart.en.md)

이 문서는 개발자가 CCOS 기여를 어디서부터 어떻게 시작하면 좋을지 안내하는 문서예요.

## 1. 이런 분께 잘 맞아요

이 문서는 아래와 같은 기여자를 떠올리며 작성했어요.

- Flutter 전문가는 아니지만 일반 프론트엔드 개발 경험이 있는 사람
- AI 도움을 활용할 수 있는 사람
- 예시와 템플릿을 따라가며 PR을 만들고 싶은 사람

## 2. 시작 전에 확인해요

먼저 읽어 보시면 좋은 문서:

- [feature_boundary.md](./feature_boundary.md)

시작 전에 아래를 확인해 주세요.

- 내 기능이 [Green / Yellow / Red](./feature_boundary.md) 중 어디에 속하는지
- 안전하게 분리된 UI 중심 기여부터 시작할 수 있는지
- 핵심 로직을 건드리지 않는지

## 3. 기여 진행 순서

1. 기능 아이디어를 경계 기준에 따라 먼저 나눠 봐요.
2. Green이면 구현 준비를 시작해 보세요.
3. Yellow면 구현 전에 코코넛 개발팀 검토를 먼저 요청해 주세요.
4. Red로 보이더라도 바로 구현하지 말고, 먼저 깃허브 이슈로 문의해 주세요.

검토 요청은 아래 채널을 기준으로 진행해 주세요.

- 기능 제안 단계라면 깃허브 이슈로 먼저 남겨 주세요. 새 이슈를 만들 때 **"CCOS Feature Proposal"** 템플릿을 선택하면 제안에 필요한 항목이 자동으로 채워져요.
- 구현 방향까지 함께 보여주고 싶다면 초안 PR로 시작해도 괜찮아요.
- Yellow 기능은 구현을 크게 진행하기 전에 먼저 이슈 또는 초안 PR에서 검토를 받아 주세요.
- Red로 보이는 기능도 바로 포기하지 말고, 깃허브 이슈를 열어 경계 판단이 맞는지 먼저 문의해 주세요.

PR이 머지되면 기본적으로 GitHub 알림으로 안내드려요. 유료 기능으로 제안하는 경우에는 [기능 제안 템플릿](./feature_proposal_template.md)이나 PR 템플릿에 남겨 주신 이메일로 계약 논의를 이어가요. 리뷰가 진행되는 동안에는 GitHub 알림을 확인해 주세요.

## 4. 브랜치 만들기

브랜치는 `develop` 기준으로 만들어 주세요.

예시:

```bash
git checkout develop
git pull origin develop
git checkout -b feat/ccos-my-feature
```

## 5. 가장 안전한 시작점

가장 안전한 시작점은 아래와 같아요.

- 안전하게 분리된 화면 영역에 새로운 UI 모듈 추가

수정을 제한하는 영역:

- 지갑 DB 관련 변경
- 서명 또는 브로드캐스트 흐름 관련 변경
- 비트코인 네트워크 이외의 서버·API 호출이 핵심인 기능

## 6. 권장 작업 순서

1. 먼저 관련 문서를 읽고, 내가 만들 기능이 어느 경계에 들어가는지 정리해 보세요.
2. 기능을 구현할 화면과 위젯은 코코넛 월렛의 기본 컴포넌트와 디자인 토큰을 기준으로 구성해 주세요.
3. 구현을 본격적으로 시작하기 전에, 이 기능이 Green인지 아니면 검토가 필요한 분류인지 한 번 더 확인해 주세요.
4. 왜 이 기능이 가능한 범위라고 봤는지와 변경 이유는, 사전 검토가 필요하면 깃허브 이슈에, 구현을 준비한 뒤 공유할 때는 초안 PR 설명에 적어 주세요.
5. 구현 범위가 애매하거나 Yellow에 가까워 보인다면, 코코넛 개발팀 검토를 먼저 받아 주세요.

## 7. 어디에서 작업하나요

CCOS 기능은 "기능 정의와 소개 정보"와 "기능이 노출되는 화면"을 나눠서 관리해요.

기본 원칙:

- 기능 메타데이터와 기능 소개 문구는 기능 폴더에 둡니다.
- 신규 기능이 기존 화면에 붙는 버튼, 카드, 메뉴 같은 진입 요소를 통해 접근된다면, 기존 화면은 최소한의 수정만 포함하도록 작성합니다.

현재 구조 예시:

```text
lib/ccos/
  ccos_feature_registry.dart

lib/ccos/features/<feature-id>/
  <feature-id>_feature.dart
  <feature-id>_feature_copy.dart

lib/screens/...
lib/widgets/features/...
```

예:

```text
lib/ccos/features/coconut_theme/
  coconut_theme_feature.dart
  coconut_theme_feature_copy.dart
```

역할:

- `*_feature.dart`
  - 기능 ID
  - 카테고리
  - 가격 / 구매 또는 활성화 관련 정보
  - 연결된 variant 또는 runtime 연결 정보
- `*_feature_copy.dart`
  - 제목: 기능의 이름
  - 설명: 기능이 무엇을 해 주는지 보여주는 소개 문구
  - 작성자: 기능을 만든 사람이나 팀 이름
  - 작성자 소개: 기능을 만든 사람이나 팀을 짧게 소개하는 문구
  - 작성 의도: 왜 이 기능을 추가했는지 설명하는 문구
  - 코코넛에 추가한 이유: 왜 이 기능이 코코넛 안에 있어야 하는지 설명하는 문구
  - 기능 도움말: 사용자가 기능의 출처나 의도를 화면 안에서 다시 확인할 수 있게 돕는 문구
  - 태그: 기능의 성격을 짧게 보여주는 항목

## 8. 기능은 어떻게 등록하나요

실제로 스토어에 올라가는 기능만 레지스트리에 등록해요.

현재는 아래 방향으로 정리하고 있어요.

- `lib/ccos/ccos_feature_registry.dart`에는 실제 등록 가능한 기능만 남깁니다.
- 레지스트리는 긴 소개 문구를 직접 들고 있지 않고, 기능별 정의를 참조해요.

예:

```dart
class CcosFeatureRegistrySource {
  static CcosFeatureListing get featuredListing => CoconutThemeFeature.listing;
}
```

정리하면 기여자는 아래 흐름으로 작업하면 돼요.

1. `lib/ccos/features/<feature-id>/` 아래에 기능 정의를 만들고
2. 레지스트리에서 그 기능을 참조하도록 연결하고
3. 실제 노출 화면(진입점)까지 직접 구현해서 PR에 포함해 주세요.

3번은 선택이 아니라 필수예요. 참고할 수 있는 예시로 테마 기능이 `theme_bottom_sheet.dart`에 붙어 있는 방식이 있지만, 이건 **테마이기 때문에 자연스러운 방식일 뿐 따라야 할 표준 패턴은 아니에요.** 기능마다 어떤 화면에 어떻게 붙는 게 자연스러운지는 크게 다르기 때문에, 여러분의 기능에 맞는 진입점을 직접 설계해서 제안해 주세요. 자세한 원칙은 [architecture.md](../foundation/architecture.md) 6.1절을 참고해 주세요.

반대로 **entitlement 연동(실제 구매 버튼, 결제 파이프라인, 영수증 검증 같은 코드)은 기여자가 구현하지 않아요.** 유료로 제안했다면 이 부분은 코코넛 개발팀이 계약 체결 후 배포 시점에 직접 연동해요. 자세한 내용은 [architecture.md](../foundation/architecture.md) 6.2절과 [monetization_guide.md](../foundation/monetization_guide.md)를 참고해 주세요.

## 9. 다국어 문구 관리 방식

- 공용 앱 문구는 중앙 i18n 파일인 `assets/i18n/*.i18n.yaml`에 둡니다.
  - 예: 공통 버튼, 전역 라벨, 여러 화면에서 반복 사용하는 기본 화면에 포함되는 문구
- 추가 기능 전용 문구는 `lib/ccos/features/<feature-id>/<feature-id>_feature_copy.dart`에 둡니다.
  - 기능 소개, 작성자 정보, 작성 의도, 코코넛에 추가한 이유, 기능 도움말, 태그 같은 문구를 포함합니다.
- 새 기능을 추가할 때는 기능 문구를 중앙 i18n 파일에 흩어 넣지 않습니다.
- 언어별 문구는 기능 폴더 아래의 `*_feature_copy.dart` 파일에서 따로 관리합니다.

예:

```dart
class CoconutThemeFeatureCopySource {
  static CoconutThemeFeatureCopy get current {
    switch (LocaleSettings.currentLocale) {
      case AppLocale.ko:
        return _ko;
      case AppLocale.en:
        return _en;
      ...
    }
  }
}
```

기여자가 새 기능을 제안할 때는 최소한 아래 언어를 함께 준비해 주세요.

- `ko`
- `en`
- `ja`
- `es`
- `de`

번역 품질은 아래 기준으로 확인해 주세요.

- 기계 번역을 사용해도 괜찮지만, 의미가 어색하지 않은지는 꼭 직접 확인해 주세요.
- 한국어 문구는 코코넛의 친근한 문체인 `~요.` 형태를 기본으로 사용해 주세요.
- 어려운 용어를 그대로 옮기기보다, 사용자가 바로 이해할 수 있도록 가능하면 쉬운 말로 풀어써 주세요.
- 개발자끼리만 이해하는 딱딱한 말투나 내부 용어는 가능하면 빼고, 일반 사용자도 읽기 쉽게 다듬어 주세요.
- 언어마다 문구 길이가 지나치게 벌어지지 않도록, 가능한 범위에서 비슷한 밀도와 길이로 맞춰 주세요.
- 작성 의도, 기능 도움말, 구매 / 활성화 설명은 특히 또렷하게 써 주시면 좋아요.
- 줄바꿈에 많이 의존한 카피는 화면 레이아웃에 따라 깨질 수 있어서 가능하면 줄여 주세요.

## 10. PR 전 체크리스트

PR을 올리기 전에 아래를 한 번 더 확인해 주세요.

- 기능 ID가 `lib/ccos/features/<feature-id>/` 폴더명과 일치하는가
- 레지스트리에는 실제 등록 항목만 연결했는가
- 기존 동작에 영향을 주는 변경이 있는지 확인했고, 있다면 어떤 영향이 있는지 설명했는가
- 기능이 허용된 경계를 벗어나지 않는지 다시 확인했는가
- 기능에 맞는 테스트를 추가했거나, 테스트를 추가하지 않은 이유를 설명했는가
- 변경된 기능을 어떤 화면과 흐름으로 확인했는지 수동 검증 내용을 정리했는가
- 필요한 문서 업데이트가 함께 포함되었는가
- 기능 소개 문구가 중앙 i18n이 아니라 기능별 문구 파일에 정리되어 있는가
- 문구의 필드 구성이 실제 코드 구조와 맞게 정리되어 있는가
- 문구가 코코넛의 톤에 맞게 쓰였는가
- 언어마다 문구 길이가 지나치게 벌어지지 않도록 정리했는가
- `ko / en / ja / es / de` 문구가 모두 준비되어 있는가
- 유료 기능으로 제안하는 경우, 제안 문서 또는 PR 템플릿에 연락 가능한 이메일을 남겼는가 (계약 논의에 필요해요)
